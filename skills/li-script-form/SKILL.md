# 脚本形式（第 6 步）

一条选题能拍成很多样子。本技能做两件事：先定这条视频是哪一类脚本，再在李同学的结构库里选一个结构，并说清用这个结构还缺哪些素材。不写开头，不写全稿。

## 判断依据

李同学把短视频脚本分成四类，按「这条视频要满足观众哪种需要」来分：

| 脚本 | 观众的需要 | 解决什么 |
|---|---|---|
| 干货 | 学到能用的 | 收获感：我听懂了、我能用、和我有关 |
| 过程（进行时） | 看下去 | 留住时间，证明能力：你正在干一件事，中间有阻碍和处理 |
| 故事 | 认识这个人 | 人设和代入：用事件、阻碍、选择和变化让人理解你 |
| 情绪 | 有人替我说话 | 找到同类用户：我想获得谁，就帮谁说话 |

所有脚本都带一点故事。一条视频以一类为主，可以带一个辅助类型；辅助类型的写作要求也要满足。

李同学讲得最重的一类是过程脚本：所有厉害的账号往往都有过程内容，它留人、流量好，也最容易把产品和人设放进去。对实体老板获客，素材里有可拍的现场时优先考虑过程。素材里没有现场，就不选过程。

四类的完整定义、写作要求和常见失败见 `references/四类脚本.md`；背后的理论见 `references/理论依据.md`。对话中不说理论名，只说人话。

## 随包材料

- `references/四类脚本.md`：四类脚本的定义、怎么选、各类写作要求和常见失败。第二步和第四步都要用。
- `references/structure-index.md`：结构索引，按四类分组，每个结构一行，写着脚本类型、难度、一句话适合和必需素材。每次都先读它。
- references/structures 目录：每个结构一个文件，文件名就是结构名。用户选定结构后，读取对应文件的「需要的素材」一节；「基本信息」里的「脚本类型」是这个结构所属的类型。

只从结构库里推荐。库里没有合适的结构时如实说明，不自己编一个结构。

## 对话原则

1. 每次只问一个问题；内容卡和对话里已有的信息不再问。
2. 先定脚本类型，再挑结构。类型说不清时不急着报结构名。
3. 推荐最多 3 个结构，每个都要说清这条视频要靠它解决什么，不只报名字。
4. 选哪个结构由用户决定。给出推荐顺序，但不替用户定。
5. 用户亲身经历的事，不能由 AI 代编。

## 固定流程

### 第一步：读出这条作品的底子

从内容卡（见文末「流水线衔接」）或对话中取得：

```markdown
选题一句话：这条视频要讲什么、从哪个角度讲（「选题与角度」）
素材：已经有的事件、经历、案例、数字、现场画面（「素材」）
受众：拍给谁看（「受众」；为空时用卡头「账号定位」里的目标用户）
本条目的：获客／流量／人设（「值不值得拍」）
转发判断：有没有人愿意转、靠什么转（「转发判断」，有就读）
账号定位：做什么生意、要什么人（卡头「账号定位」）
```

- 「本条目的」卡里没有时，按账号定位默认取「获客」，并在第二步的依据里写明。
- 没有选题时，说明这一步需要先有选题，建议回到第 3 步；用户坚持直接选形式时，请他用一句话说出想讲的事。
- 素材里只写了「有个事」，没写有没有现场画面、是不是亲身经历时，第二步前问一句最影响判断的（通常是：「这件事当时有没有拍下来，或者以后还能去现场拍？」）。

### 第二步：定脚本类型

按 `references/四类脚本.md` 的三个问题依次判断：

1. **这条主要想让观众得到什么？** 学到能用的东西 → 干货；看完一件正在发生的事 → 过程；认识这个人 → 故事；被说中心里话 → 情绪。
2. **素材支持吗？** 逐类核对，不支持的类直接排除：
   - 没有可拍的现场（当时没拍、以后也去不了现场、过程不能公开），做不了过程；
   - 没有用户自己或身边人的亲身经历，做不了故事；
   - 说不出这条想要的是哪群人、站在他们哪一边，做不了情绪；
   - 拿不出真实可用的方法、判断或信息，做不了干货（收获感不能靠虚构效果）。
3. **和本条目的一致吗？** 获客常用过程和干货；立人设常用故事；要互动、找同类常用情绪。转发判断里写着「靠替人说话、站队转发」时，可以把情绪当辅助类型。

判定规则：

- 第 1 问和第 3 问指向不同类型时，以第 3 问（本条目的）为准，第 1 问指向的那类当辅助类型，前提是素材支持。
- 本条目的是获客、素材里有可拍现场（门店、工地、工厂、上门服务、出了状况被拍下来）时，先看过程能不能成立：有一件正在做的事，中间有阻碍或意外。成立就定过程为主类型；只有成品、没有中间经过时，不硬定过程。
- 辅助类型最多一个，只在素材也支持时才写。没有就写「无」。
- 四类都不支持时（例如只有一句感慨），如实说明缺什么，建议回第 2 步补素材，或请用户补一件具体的事。

用一两句话告诉用户判断结果和依据，例如：

> 这条我判成过程脚本（辅助：故事）。你想让人看完相信你能接住临时状况，本条是获客；你手上有现场视频，中间有物业拦车这个阻碍，过程能成立。

### 第三步：推荐 2–3 个结构

读取 `references/structure-index.md`，从主类型对应的那一组里挑 2–3 个；素材强烈支持另一组的某个结构时（例如定了情绪，但手上正好有一次完整的翻车救场现场），可以跨组放一个，并写明为什么跨组。

每个候选写：

```markdown
**结构名**（脚本类型｜难度）
为什么适合这条选题：这条视频要解决什么（例如让同城办聚会的人信你能临时救场），这个结构怎么帮它解决
需要的素材：照索引「必需素材」列
你已经有的：对应到用户的哪条素材
还缺的：……
```

- 推荐前可以问 1–2 个可行性问题（例如能不能再去现场补拍、有没有员工愿意出镜），不计入第四步的追问次数。
- 排序：先看素材缺口小不小，再看脚本类型是否和主类型一致，最后看难度。跨组的候选排在同组之后，除非它缺口明显最小。
- 选题明显是城市印象或故事 Vlog 时，按索引最后一节转到 `li-city-impressions` 或 `li-story-vlog`，并说明原因。

然后停下问：

> 你想用哪一个？也可以说说哪个最不像你会拍的。

用户选定前，不进入第四步，不更新内容卡。

### 第四步：列出素材缺口

用户选定后，读取该结构文件的「需要的素材」表，逐项对照：

| 素材 | 状态 | 处理 |
|---|---|---|
| …… | 已有／缺 | 已有：写出用哪条素材；缺：按表里「缺了怎么办」处理 |

缺口的处理：

- **追问**：一次只问一个，最多问 3 个最关键的；先问用户一句话就能答的（账号名、原话、具体数字），再问需要回忆的；
- **占位**：第 8 步写稿时写成【待补：……】，现在只记下来；
- **可起草**：只限常识类素材，第 8 步写成【示例，请改成你的】。来源写「用户亲历」的素材一律不可起草，只能追问或占位。

用户说「先写吧」时停止逐个追问：把剩下的缺口一次列出来，告诉用户能顺手答的现在就答，答不上的全部转成占位。不让追问卡住流程。

**再对照该类写作要求**：打开 `references/四类脚本.md` 里主类型（有辅助类型时也看辅助类型）的写作要求，逐项看这条素材缺哪几项，只列缺的：

- 过程：起因、期待、过程、阻碍、槽点、信息、惊喜、人设、产品九项。最常缺阻碍（一路顺利）和槽点（观众没什么可说的）；
- 故事：值得讲的理由、内心动荡、性格、具体画面、阻碍、变化、最后的认知或行动七项；
- 情绪：想要谁、账号长期要谁、这群人想听什么、想做缺理由的事、不想做缺借口的事五问；
- 干货：语言简单、具体可操作、对应生活场景、信息密度和转折、跨领域新鲜感、留评论的理由。

这部分不追问，写成第 8 步写稿时要补的提醒。和素材表重复的项只算一次。

### 第五步：交付

素材缺口按素材表里状态为「缺」的行数计算；写作要求的缺口另列，不计入这个数。

```markdown
## 脚本形式

脚本类型：主类型（辅助：……／无）
判断依据：一两句话
选定结构：结构名（脚本类型｜难度）
为什么用它：一句话，落到这条视频要解决什么
素材对照：
- 已有：……
- 待补：……（第 8 步会写成占位）
- 可起草：……
该类写作要求的缺口（第 8 步写稿时补）：
- 过程｜阻碍：……
- 过程｜槽点：……
```

## 质量检查

- 是否先读了选题、素材、受众（或账号定位里的目标用户）和本条目的，再判断？
- 脚本类型是否按三个问题判断，并用一两句话告诉了用户依据？
- 是否核对了素材支持：没现场没选过程，没亲身经历没选故事，没目标人群和立场没选情绪？
- 获客且有可拍现场时，是否先考虑了过程；素材没现场时，是否没有硬推过程？
- 辅助类型是否最多一个，且素材支持？
- 推荐是否都来自索引里对应的那一组（跨组时写了理由），最多 3 个，每个写清要解决什么、已有和还缺？
- 排序是否按缺口小、类型一致、难度？
- 是否停下来由用户选定结构？
- 素材缺口是否逐项对照了结构文件的「需要的素材」表，没有凭印象下判断？
- 是否列出了该类写作要求的缺口，作为第 8 步的提醒？
- 是否没有替用户编造亲身经历？追问是否一次一个、最多 3 个，用户要先写时是否立即停止？

## 内联案例（示范）

以下两个案例是示范，用来说明判断方式，不是真实用户记录。

### 正例：烤羊老板临时救场 → 过程脚本

- 素材：做上门烤全羊的老板。客户下午临时决定晚上在别墅办聚会，只剩 3 小时；车被物业拦在门口，羊要现场处理，客户一直担心来不及。老板协调进场、现场开烤，最后按时上桌。员工用手机拍了大部分经过。
- 底子：本条目的是获客；受众为空，按账号定位取「同城办聚会、订烤羊的人」。
- 第二步：想让人看完相信「这个老板能接住我的临时状况」，指向过程；有现场视频、有物业拦车和时间紧两个阻碍，过程成立；获客也常用过程。判为过程脚本，辅助：故事（老板顶着压力救场，能看出性格）。
- 第三步：从过程组里推荐。
  1. **服务业-翻车完美收场**（过程（辅：故事）｜3 级）：这条要解决的是让客户信你能在突发状况下按时交付，这个结构就是「出状况 → 处理 → 圆满收尾」。已有：出了什么状况、现场画面、最终结果；还缺：发现时的第一反应原话、和客户沟通的话、收尾金句。
  2. **电商型-发货展示**（过程｜1 级）：难度低，但它展示的是批量发货和客户关系，这条没有发货场景，缺口大，排第二只作备选。
- 第四步对照写作要求：起因、阻碍、过程、惊喜都有；缺槽点（观众能评论什么，例如「别墅区为什么不让烤羊车进」）和产品（观众看完知不知道可以上门烤），写进第 8 步提醒。
- 结尾：✅ 第 6 步完成：过程脚本，选定「服务业-翻车完美收场」，素材缺口 3 项

### 反例：只有观点，硬选成过程脚本

- 素材：装修公司老板只想说「装修千万别找报价最低的那家」，手上没有工地画面，也没有正在进行的项目可以跟拍。
- 错误做法：因为「过程流量好」，直接推荐「服务业-探工地」，然后把工地画面、业主满意度全部列成待补。缺口大到第 8 步只能编，过程也看不到真实阻碍。
- 正确做法：第 2 问核对素材，没有可拍现场，排除过程。他想让准备装修的人觉得「有人替我说出了心里的担心」，有明确的目标人群和立场，判为情绪脚本；如果他能讲清两三个低价报价后来加钱的具体坑，辅助：干货。推荐情绪组的「观点型-错误对比-三举例」（不需要真实案例，日常观察就够）；手上有带数字的真实客户踩坑案例时，再加「观点型-强观点钩子-三论点」。同时告诉他：以后有在建工地能拍，这个题可以再做一条过程版。

## 流水线衔接：内容卡与下一步

本技能是李同学「一步一技能」12 步中的第 6 步「脚本形式」。单独使用时照常执行上文流程；从 `li` 主入口或上一步「继续」进来时，按下面衔接。

**内容卡**：用户当前工作目录里的 `内容卡_<主题>.md`，一条作品一张，栏目固定为：素材 / 选题与角度 / 受众 / 值不值得拍 / 转发判断 / 形式 / 开头 / 脚本 / 审核记录 / 发布，卡头有「当前进度」和「账号定位」两行。

- 开始前查找 `内容卡_*.md`：有一张就读取，沿用已确认的内容，不让用户重复提交；有多张先问是哪一条；用户粘贴了「交接卡」就以它为准。没有卡时，在用户做出第一个确认后新建，空栏目写「（待填）」。
- 读卡时：「选题与角度」「素材」「受众」里已确认的内容直接用于第一步和第四步；「值不值得拍」里的本条目的、「转发判断」和卡头「账号定位」用于第二步定脚本类型；缺什么再问。
- 本技能只更新「形式」（写第五步的交付内容：脚本类型主＋辅、判断依据、选定结构、为什么用它、素材对照、该类写作要求的缺口）和卡头「当前进度」；本步用户新补充的素材写进「形式」的素材对照，第 7、8 步以它为素材来源，写作要求的缺口是第 8 步写稿时要补的提醒；其他栏目只读。发现与其他栏目矛盾时告诉用户，由用户决定。只写用户确认过的短结论，不贴完整分析。
- 「受众」为空时，以卡头「账号定位」里的目标用户为准，不再追问。
- 不能写文件的客户端（如豆包、网页对话）：在回复末尾输出一个代码块，第一行写「【交接卡】复制整段，下一步发给我」，下面是整张卡的最新内容。

**带练模式（默认）**：选哪个结构由用户决定——到这个判断点必须停下，给出脚本类型、候选和推荐顺序，等用户选。用户选完、素材对照完成后，才更新内容卡并输出下面的结尾。用户回复「继续」时，定位并读取下一步技能的 SKILL.md（宿主已发现的技能路径，或同级目录按机器名称查找），带着内容卡进入；不越过用户的选择自动连跑。

**结尾格式**：

```
✅ 第 6 步完成：<脚本类型>脚本，选定「<结构名>」，素材缺口 <N> 项
👉 下一步是第 7 步：开头（li-script-opening 开头），回复「继续」开始
也可以：回到第 3 步换选题角度 ／ 先补齐待补素材再继续
```

选中城市印象或故事 Vlog 时，👉 一行改为转到 `li-city-impressions` 或 `li-story-vlog`，它们自带第 6–8 步。
